# ADR-001: 実装言語に Go を採用する

- **状態**: Accepted
- **日付**: 2026-09-05
- **関連**: #1

## Context

### このリポジトリが置くもの

書籍検索 API の単体サービス。書誌データを自前の PostgreSQL に投入し、
**検索の実装を既製品から自前実装へ段階的に深めていく**（段階の定義は ADR-003）。

目的は検索機能を提供することではなく、**各段階のレイテンシを実測して比較すること**にある。

### 必要な機能

- 書誌データを外部から取得し、PostgreSQL に一括投入するバッチ
- 検索クエリを受ける HTTP API
- 検索の実装を段階的に差し替えられること（最終的に転置インデックスと BM25 を自前実装する）
- 各段階のレイテンシを計測し、段階間で比較できること

### 言語に求める要件

| # | 要件 | 理由 |
|---|---|---|
| 1 | 段階ごとのレイテンシを**同一の道具で計測・比較できる** | 段階間の比較が成果物そのものであるため |
| 2 | HTTP から DB までの経路を**薄く書ける** | アプリ側の処理が実測レイテンシに乗ると、原因の切り分けが増えるため |
| 3 | **データ構造の自前実装に耐える**（静的型・実行性能） | 転置インデックスと BM25 を自前で書くため |
| 4 | 学習コストが有界であること | 可処分時間が週 10〜12h に限られるため |

## Decision

**Go を採用する。**

採用理由は**実行速度ではない**。検索が PostgreSQL 側で完結する段階では
レイテンシは DB が支配的であり、言語による差は観測されない見込みである。
「Go は速い」を根拠にすると、最初のレイテンシ実測で本 ADR は破綻する。

要件との対応は以下のとおり。

- **要件1** — ベンチマーク（`go test -bench` / `testing.B`）とプロファイル（`net/http/pprof`）が
  標準ツールチェインに含まれる。`-benchmem` でアロケーションまで分解でき、
  全段階を同一の道具で横並びに測れる
- **要件2** — `net/http` + pgx で足り、Web フレームワークを挟まずに書ける
- **要件3** — 静的型があり、posting list やスコアラーのようなデータ構造を直接書ける。
  実行性能も既製品（C 実装）との比較に耐える
- **要件4** — 言語仕様が小さく、標準ライブラリ中心で完結する

### 前提条件

**自前の転置インデックスをアプリケーション側に持つことを前提とする。**
PostgreSQL のテーブル内に持つ設計に変えた場合、要件3 が消える。

## 選ばなかった選択肢

### Ruby

学習コストがゼロで、検索が PostgreSQL 側で完結する段階までは十分成立する。

採用しなかったのは**要件3** による。自前の転置インデックスを書いたとき、
**遅さが言語由来かアルゴリズム由来かを切り分けられない。**
既製品との性能比較を成果物に含む以上、この切り分け不能は許容できない。

### Rust

要件1〜3 は満たすが、**要件4** を満たさない。習得に要する時間が読めない。

### Python

要件1〜2 は満たすが、検索ライブラリが揃いすぎており、
**既製品を使わずに中身を書く**という本プロジェクトの趣旨と競合する。

## Consequences

- Go の実装経験はチュートリアル通過程度であるため、当面の使用範囲を
  標準ライブラリ（`net/http`、`encoding/json`、`log/slog`、`testing`）と pgx に限定する。
  Web フレームワークは採用しない
- 自前の転置インデックスを PostgreSQL 内に持つ設計へ変更する場合、
  要件3 が失われるため本 ADR を見直す
