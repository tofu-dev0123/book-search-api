# ADR-002: 書誌データのデータソースに openBD を採用する

- **状態**: Accepted
- **日付**: 2026-09-05
- **関連**: #2

## Context

### 何を決めるのか

書誌データの取得元を決める。本 ADR が決めるのは**検索コーパスの供給元**であり、
書影の供給元は含まない（ADR-004 で決める）。両者は別のソースになる。

### 解こうとしている問題

Shelfie の現行検索は楽天ブックス API に `title:` を投げる部分一致のみである。

- **著者名で引けない**
- **読みで引けない**（「たつじんぷろぐらまー」がヒットしない）
- 表記ゆれに弱い

この欠陥の解消が、検索を自前実装する実用上の動機である。

### データソースに求める要件

| # | 要件 | 理由 |
|---|---|---|
| 1 | 全件を一括取得し、自前の PostgreSQL に投入できる | 自前の転置インデックスを持つため（ADR-001 要件3）。外部 API への問い合わせで代替できない |
| 2 | 日本語書籍を網羅している | Shelfie に登録される本が引けなければ実用にならない |
| 3 | 著者名と読みを検索対象として持つ | 上記の欠陥を解消するため |
| 4 | ライセンスが実サービスでの利用を許諾している | 実用 API として公開するため |

**要件1 が最も強い制約である。** 候補の大半はここで落ちる。

## Decision

**openBD を採用する。**

要件との対応は以下のとおり。

- **要件1** — openBD は「**全件取得やデータ同期を推奨する API 設計**」を公式に明示している。
  一括取得を禁じる API が通例であるため、これは異例の設計方針である。
  実測で `978-4` の 1,719,946 件を **2時間15分 / 生 JSON 2.6GB** で取得できる見込み
  （1,000件 POST = 4.7秒 の実測から算出）
- **要件2** — Shelfie に実際に登録された 16 冊で収録率 **16/16 (100%)**
- **要件3** — ONIX の `collationkey` にカタカナ読みを持つ。実登録 16 冊で **16/16 (100%)**。
  タイトルと著者名の両方に付く（`いもうと・泡天国` → `イモウト アワ テンゴク`、
  `河里, 一伸` → `カワザト, カズノブ`）。**これが決定的な採用理由である**
- **要件4** — 「本の販促・紹介目的に限り」個人・団体・企業を問わず無償で利用できる

### openBD の実像（採用にあたり把握しておくこと）

カーリル（API インフラ運用）と版元ドットコム（書誌データ整備）の共同プロジェクト。
**2023年に構造が変わっており、現在は2層になっている。**

- **2023-06-05** JPO 出版情報登録センター（JPRO）から版元ドットコムへの配信が停止
- **2023-07-25** 「API v1 の提供終了」を告知。公式理由は
  「書誌も含めて再配信は現行規約違反との方針が示され」オープン提供の継続が困難になったため
- **2023-08-28** JPRO 由来のデータを**国立国会図書館の書誌に差し替え**。
  公式に「書影の収録範囲は大幅に減少する見込み」と明記

| 層 | 書影 | 内容紹介 |
|---|---|---|
| 版元ドットコム会員社（520社）の本 | あり | あり |
| それ以外（NDL 書誌の ONIX 簡易変換） | なし | なし |

**この2層構造が実測値をすべて説明する。**
2,000件の無作為抽出で書影 5.2%・内容紹介 6.7%・目次 12.1% にとどまるのは、
版元ドットコム会員社の本の割合がその程度であるためである。
著者名が NDL 典拠形式（`原,隆文,1965-`）なのも、書影率が 2023年以降も改善しない
（2023年以降で 7.5%）のも、同じ原因による。

### 前提条件

**書影は openBD から得られないことを前提とする。**
実登録 16 冊での書影保有は **0/16**、母集団推定でも 5.2% である。
書影は別ソース（ADR-004）から供給する。書影の網羅性を openBD に求める設計に変えた場合、
本 ADR は成立しない。

## 選ばなかった選択肢

### 国立国会図書館サーチ

**最後まで残った対立候補である。** 落とした理由は要件を満たさないからではなく、
**openBD が実質的に NDL 書誌の上位互換になっているため**である。

前述のとおり、現在の openBD の大半は NDL 書誌を ONIX 形式に変換したものである。つまり

- NDL 書誌の内容は openBD 経由でも得られる
- openBD には**版元ドットコム会員社分の書影と内容紹介が上乗せ**されている
- openBD は ONIX 形式に整形済みで、1リクエスト 1,000件の単純な API で取れる。
  NDL を直接使う場合は OAI-PMH / SRU のハーベストを自前で実装する必要がある

要件1〜3 は NDL でも満たせる見込みだが、**同じデータをより高い実装コストで取得することになる。**

なお NDL も `dcndl:titleTranscription` / `dcndl:creatorTranscription` で読みを持つ
（OpenSearch API で確認済み）。要件3 の観点では遜色ない。

**未実測の点**: NDL の一括ハーベストの所要時間と総件数は測っていない。
`ndlsearch.ndl.go.jp/thumbnail/` は 403（CloudFront によるブロック）で、
WAF の判定か非営利限定の制限かは切り分けていない。
openBD が停止した場合の移行先として、改めて評価する必要がある。

### 楽天ブックス API

**要件1 を満たさない。** 提供されているのは ISBN 指定の 1 件引きと、
クエリに対するページング付きの検索のみで、**全件を走査する手段が無い。**
自前コーパスの土台にできない。

**未実測の点**: 1リクエストあたりの上限件数とページング上限は API ドキュメントで
確認していない（Shelfie の既存クライアントは 1リクエスト 20件で利用している）。
ただし全件走査の入口が無いことは変わらないため、要件1 の判定は覆らない。

一方で**書影は実登録 16 冊で 16/16 (100%)** と網羅的である。
このため書影の供給元としては採用する（ADR-004）。
書誌の供給元としては落とし、書影の供給元としては採る、という使い分けになる。

### Google Books API

**要件1 を満たさない。** 無認証のアクセスで即座に HTTP 429（レート制限）が返り、
1件も取得できなかった。認証を付けた場合の上限は未実測だが、
Volumes API は検索用のインターフェースであり全件取得の手段を提供していない。
規約上もクロールと蓄積が制限される。

### カーリル

**土俵が違う。** 図書館の蔵書所在検索であり、書誌メタデータの供給元ではない。
（なお openBD の API インフラはカーリルが運用している）

## Consequences

- **検索対象は title / author / 読み（`collationkey`）を主軸とする。**
  内容紹介は 6.7% しか無いため、内容ベースの検索は当面成立しない。
  Shelfie の用途は known-item search（既に知っている本を登録するために探す）であり、
  この制約は実用上許容できる
- **正規化が必要になる。** 著者名が NDL 典拠形式（`原,隆文,1965-`）のため
  「原隆文」で検索してもそのままではマッチしない。
  タイトルは ` : ` でサブタイトルを区切る（標本の 31%）
- **規約の「データを任意に改変してはいけません」との関係。**
  検索用の正規化済みインデックスは別に保持し、**API が返す書誌データは openBD 由来のまま保つ。**
  改変の禁止は提供データの書き換えを指すものと解釈する
- **規約は「利用権を第三者に貸与、譲渡、売買」することを禁じている。**
  本 API は Shelfie への提供にとどめ、第三者への汎用検索 API としては公開しない
- **キャッシュしたデータは変更を早く反映する義務がある。**
  規約に「利用側の事情で書誌データをキャッシュする場合は、データの変更をできるだけ早く
  反映するようにしてください」とあるため、差分同期の仕組みが必要になる。
  個別の削除要請にも従う必要がある

### 引き受けるリスク

**openBD API v1 は 2023-07 に「技術的な調整が完了次第、すみやかに提供を終了」と
告知されたまま、3年後の 2026-09-05 現在も稼働している。**

- 今日の実測: `v1/coverage` が HTTP 200（21秒）、`v1/get` が HTTP 200（0.18秒）
- **v2 は存在しない**（`api.openbd.jp/v2/coverage` は 404）。
  2024-08 に「openBD バージョン2に向けて」のカンファレンス開催の記録はあるが、
  その後の公開情報は見つからない
- 規約は「プロジェクトが必要と判断した場合、利用者への何らの通知なく、
  また、一切の責任を負うことなく、APIの使用を制限または停止できる」と定める

要件1 を満たす他の選択肢が無いため、**このリスクは引き受ける。**
停止した場合の移行先は国立国会図書館サーチとする。
現行の openBD データが NDL 書誌ベースであることから、移行後もコーパスの中身は
大きく変わらない見込みである（書影 5.2% と内容紹介 6.7% を失う）。

投入処理は**取得元を差し替えられる形で実装する**こと。
